# Fullstack Node.js Developer — приложение и интеграция

## Цель

Собрать единственный работающий end-to-end путь: параметры заказа → API → точная eligibility-фильтрация → стабильные максимум три карточки с объяснениями.

## Принятый контракт

Основной API: `POST /api/recommendations`. Полный запрос/ответ и три значения `outcome` зафиксированы в [общем README](../README.md). Изменения контракта сначала обсуждать и записывать там.

Основные обязательные поля: `city`, `date` (`YYYY-MM-DD`), `eventFormat`, `category`, `budgetKzt` (неотрицательное целое). Опционально: `language`, `maxHours`.

Алгоритм:

1. Проверить город+категорию — если профилей нет, `category_unavailable`.
2. Исключить профили, занятые по точному `busy_dates`.
3. Исключить цену выше бюджета.
4. Исключить неподходящий `event_formats`.
5. Применить заданные язык и длительность (`max_hours: null` означает, что присутствие по часам не ограничено).
6. Устойчиво сортировать прошедших по `price_from_kzt` по возрастанию, затем по `id`; никакой случайности и LLM в сортировке.
7. Построить 1–2 проверяемых объяснения: совпадения + цена относительно бюджета + highlight из описания, если доступен.

Причины нулевой выдачи должны происходить из фактических подсчётов этапов, а не быть общим текстом.

## Статус и зависимости

- Статус: начать контракт и мок matcher/UI независимо от коллег.
- Входящий блокер: нет. Полный CSV доступен в `../data/contractors.csv`.
- От PropTech: подтверждение значений/семантики категорий, даты и причин исключения.
- От ML: `highlights.json`; приложение должно работать до его появления.
- Готово, когда: приложение показывает согласованный результат для любого валидного запроса и понятный нулевой результат; порядок для идентичного запроса повторяем.
