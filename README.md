# HackAlem AI — умный подбор event-подрядчиков

## 1. Анализ задачи

Сервис не создаёт каталог и не оформляет бронь. Заказчик уже выбрал город и тип услуги, поэтому продукт должен сузить выбор до максимум трёх реально подходящих профилей и объяснить, чем каждый из них подходит именно под параметры заказа.

**Пользовательский путь:** заказчик задаёт город, дату, тип мероприятия, категорию и бюджет (при необходимости язык и длительность) → сервис сначала исключает неподходящих и занятых на эту дату → ранжирует оставшихся → показывает до трёх карточек с проверяемыми причинами.

Данные: 66 анонимных профилей; доступные категории, города Алматы / Астана / Зарубежье, цены, форматы, языки, максимальная длительность, занятые даты в окне 23.09.2026–31.12.2026 и свободные описания. У 13 профилей флаг synthetic; часть цен и городов имеет imputed-флаги. Эти признаки нельзя скрывать в UI.

## 2. Проблема и пользователь

- **Проблема:** заказчику приходится вручную сравнивать длинный список; занятый подрядчик или цена выше бюджета делают рекомендацию бесполезной.
- **Пользователь:** заказчик мероприятия в Казахстане, который уже знает город, дату, формат и категорию нужного подрядчика.
- **Вход:** обязательные город, дата, формат мероприятия, категория и бюджет; опциональные язык и длительность в часах.
- **Обработка:** точная фильтрация по обязательным требованиям, затем детерминированное ранжирование и построение объяснений из фактов профиля.
- **Результат/ценность:** до трёх карточек с конкретным соответствием; если выбора нет — понятное состояние и причина.

## 3. Предлагаемое решение

Один Node.js-сервис с прозрачным rule-based matching. Для 66 профилей и структурированных критериев отдельная обученная ML-модель не нужна: приложение извлекает короткий фрагмент непосредственно из описания профиля и соединяет его с конкретными совпадениями по формату, дате и бюджету. Объяснения проверяемые и детерминированные; внешняя AI-модель не влияет на eligibility или порядок. Не обещать бронь или подтверждённую доступность вне календаря.

Основная ценность — конкретность объяснений: например, «Работает на свадьбах; говорит на казахском и русском; цена 250 000 ₸ укладывается в бюджет 300 000 ₸; в описании специализируется на выездных церемониях». Для каждого факта сохранять источник (поле профиля или highlight описания); не генерировать неподтверждённые сведения.

## 4. MVP

### MUST HAVE

- Форма запроса с обязательными пятью полями и опциональными языком/длительностью.
- Фильтрация города + категории; занятый в дату подрядчик никогда не показывается; формат и бюджет обязательны; заданные пользователем язык/длительность также должны выполняться.
- До трёх карточек с именем, категорией, городом, ценой и 1–2 специфичными предложениями, собранными из подтверждённых совпадений и особенностей описания.
- Явные три исхода: `matched`, `category_unavailable`, `no_eligible_candidates`; при менее чем трёх результатах показать найденное количество и объяснить дефицит.
- Детерминированный порядок; один и тот же запрос даёт один и тот же порядок.
- Показ флагов `synthetic`, `price_imputed`, `city_imputed` там, где они есть.
- На демо обязательны плотная категория на осеннюю дату, редкая категория и запрос без результата. Конкретные параметры выбраны из CSV в разделе Demo Flow ниже.

### SHOULD HAVE

- Опциональные фильтры языка и максимальной длительности.
- Отображение breakdown причин отказа (занят / выше бюджета / не берёт формат / не соответствует дополнительному фильтру).
- Контрольная панель с исходным описанием/выделенными фактами для объяснения пайплайна жюри.

### NICE TO HAVE

- Дополнительные синтетические профили только при нехватке реальных демонстрационных примеров; явно маркировать их и не подменять реальные данные.
- Экспорт/сохранение подбора. Бронирование, заявки и уведомления вне задачи.

## 5. Архитектура

```text
HTML/CSS/JS UI → Node.js HTTP API → CSV каталог
                                  ├─ eligibility + сортировка по цене
                                  └─ explanation builder ← фрагмент description
```

- **Frontend:** форма и карточки трёх исходов на обычных HTML/CSS/JS.
- **Backend:** Node.js на стандартных модулях без пакетов: валидация, фильтры, сортировка и объяснения.
- **Каталог:** `data/contractors.csv` — локальный источник данных MVP; база не нужна.
- **ML:** не включён в критический путь; структурированные условия и извлечение фрагмента из описания не требуют обученной модели.

## 6. ML Developer

Отдельная модель для MVP не нужна: запрос состоит из структурированных полей, а выводимые объяснения извлекаются из текстов профилей. На оставшееся время отдельный ML-сервис и обучение модели не создавать. Текущая реализация выбирает фразу из исходного описания и связывает её с фактами фильтрации; это обеспечивает проверяемые, воспроизводимые ответы без AI API.

## 7. Fullstack Node.js Developer

- **Цель:** владелец работающего end-to-end приложения и API.
- **Задачи по порядку:** реализованы единый Node HTTP сервер, форма, чтение CSV, метаданные формы, три исхода, жёсткая фильтрация, сортировка по цене/ID и фактические объяснения.
- **Точка запуска:** `node server.js`; приложение раздаётся на `http://localhost:3000`.
- **Зависимости:** только установленный Node.js; внешние пакеты и ключи не требуются.

## 8. PropTech Developer

- **Цель:** формализовать корректный смысл критериев подбора и проверяемые причины.
- **Задачи:** предметные правила зафиксированы; три demo-запроса и фактические результаты по календарю подобраны из CSV; флаги происхождения данных показываются на карточках.

## 9. API и Data Contracts

### `POST /api/recommendations`

Request:

```json
{
  "city": "Алматы",
  "date": "2026-10-03",
  "eventFormat": "свадьба",
  "category": "Ведущий",
  "budgetKzt": 2000000,
  "language": "",
  "maxHours": null
}
```

`language` и `maxHours` опциональны. `budgetKzt` — целое число в тенге; `date` — ISO `YYYY-MM-DD`. `eventFormat` — формат мероприятия из каталога. Не вводить свободные строки для категорий/форматов в MVP; варианты брать из каталога.

Response при подборе:

```json
{
  "outcome": "matched",
  "matchedCount": 1,
  "shownCount": 1,
  "categoryCount": 10,
  "cards": [
    {
      "id": "HK-72938",
      "name": "Софи Хаттер",
      "categories": ["Ведущий"],
      "city": "Алматы",
      "priceFromKzt": 2000000,
      "synthetic": false,
      "priceImputed": false,
      "cityImputed": false,
      "languages": ["казахский", "русский"],
      "maxHours": 8,
      "reasons": ["Берёт формат «свадьба»; свободен 3 октября по календарю; цена от 2 000 000 ₸ совпадает с бюджетом.", "В описании: «Ведущий, актер, участник КВН команды „Ghibli Микс“ — Высшая лига». "]
    }
  ],
  "message": "В городе есть профили этой категории: 10. Условиям соответствуют: 1. Исключены: 4 не берут этот формат, 5 заняты на выбранную дату.",
  "rejectionCounts": { "eventFormat": 4, "busyOnDate": 5, "overBudget": 0 }
}
```

Response без результата использует тот же формат с `cards: []`, `matchedCount: 0`, человекочитаемым `message` и `outcome`:

- `category_unavailable` — в заданном городе нет ни одного профиля требуемой категории.
- `no_eligible_candidates` — категория в городе есть, но каждый кандидат исключён хотя бы одним заданным условием; `message` называет фактическую причину/причины.
- `matched` — есть от 1 до 3 карточек; если меньше трёх, `message` говорит, сколько нашлось и почему остальных нет.

Ошибки: `400` для неверной даты, пустого обязательного поля, отрицательного бюджета, неподдерживаемого значения категории/формата/языка или даты вне календаря; `500` только при внутренней ошибке с безопасным коротким сообщением. Endpoint не вызывает LLM на каждый запрос.

### `GET /api/meta?city=Алматы`

Возвращает списки `cities`, все `categories`, `categoriesInCity` для справки, `eventFormats`, `languages`, `calendarRange` и число профилей. В форме показаны все категории, чтобы пользователь мог явно получить исход `category_unavailable`.

### Правило отбора и порядка

1. Сначала определить наличие категории в городе: это отделяет `category_unavailable`.
2. Удалить профили, не принимающие `eventFormat`.
3. Удалить занятых на точную дату.
4. Удалить профили, чья `price_from_kzt` выше бюджета.
5. Если пользователь указал язык/длительность — удалить несовпадающих; `max_hours: null` означает длительность не привязана к присутствию.
6. После eligibility сортировать по `price_from_kzt` по возрастанию, затем по `id` по возрастанию. Это понятный детерминированный порядок по цене предложения, а не оценка качества подрядчика; цена «от» и imputed-флаг должны быть видны. Одинаковый запрос не зависит от случайности/LLM.
7. Сформировать 1–2 предложения из реальных совпадений, цены, календаря и фрагмента описания. Не говорить «лучший» или «доступен для брони».

### Каталог

Сохранить исходные поля датасета: `id`, `anon_name`, `categories`, `city`, `price_from_kzt`, `event_formats`, `languages`, `max_hours`, `busy_dates`, `description`, `synthetic`, `city_imputed`, `price_imputed`. Имена не интерпретировать как реальные. `busy_dates` — точный список; summary «занято N из 100 дней» не заменяет календарь.

## 14. Приоритеты при нехватке времени

- **Осталось 50% (2 часа):** оставить основной сценарий и конкретные объяснения; отключить опциональные язык/длительность и ML highlights, если задерживают интеграцию.
- **Осталось 25% (1 час):** обязательны три исхода API, точный календарь, фильтры бюджета/формата и UI карточек/пустого результата; стек и контракты заморожены.
- **Остался 1 час:** scope уже заморожен; довести один вертикальный путь на CSV и три подготовленных запроса.
- **Осталось 30 минут:** только запуск приложения и переключение между demo-запросами; никаких новых функций и изменений каталога.

## 15. Demo Flow

CSV содержит полные `busy_dates`, поэтому demo-запросы выбраны по данным:

1. **Плотная категория, осень:** Алматы, `2026-10-07`, `свадьба`, `Ведущий`, бюджет `2 000 000 ₸`. Шесть профилей проходят дату/формат/бюджет; порядок по цене выводит `HK-44923`, затем `HK-35215` и `HK-42352` (равная цена — по `id`). Тот же запрос на `2026-10-03` оставляет только `HK-72938` (Софи Хаттер): остальные пять заняты; объяснить смену выдачи календарём.
2. **Редкая категория:** Алматы, `2026-10-07`, `свадьба`, `Инструменталист`, бюджет `600 000 ₸`. Все три профиля категории проходят дату и формат; порядок по цене: `HK-46450`, `HK-90013`, `HK-74147`. `HK-90013` синтетический и должен иметь метку.
3. **Нет результата:** Алматы, `2026-10-07`, `свадьба`, `Ведущий`, бюджет `500 000 ₸`. Категория есть, но все шесть кандидатов дороже бюджета; ожидаемый исход `no_eligible_candidates` с явной причиной.
4. **Категория недоступна:** Зарубежье, `2026-10-07`, `свадьба`, `Флорист`, бюджет `1 500 000 ₸`; ожидаемый исход `category_unavailable`.

На каждом примере показать вход, результат и объяснение; для одного профиля обратить внимание на synthetic/imputed маркировку. Для сравнения открыть соседний демо-запрос с датой 3 октября: выдача меняется из-за занятости.
